# OSC 7501 — how Muster speaks the Program Status Protocol

Muster's session state is the [Program Status Protocol][spec] (OSC 7501), the
terminal-native way for a program to report what it is doing.

On this branch there is **one writer**: `bin/muster-tap`. It runs an agent on a
pty, forwards every byte unchanged, answers the protocol's feature probe
itself, and — when it sees a report in the stream — writes that report as a
Muster JSON record. The record is the bar's input; the bar never reads the
terminal and never talks to the agent.

```
agent ──OSC 7501 on its pty──▶ muster-tap ──one JSON record──▶ sessions/ ──▶ the bar
```

There is no second writer in this branch: no report script, no agent bridge,
no hook. An agent that does not speak OSC 7501 itself is not a session here.

[spec]: https://www.superlogical.com/rex/docs/build/program-status

The protocol was published on 2026-10-06 and is at revision 0.4. Agents ship it
now — Claude Code 2.1.295, pi 1.1.0, Crush 0.98.0, omp 18.8.7, Codex 0.163.0,
Docker Agent 1.150.0, Factory Droid 0.236.0 — and
[`docs/native-emitters.md`](native-emitters.md) has the matrix with the
upstream evidence.

**The protocol has no read API.** The records live in the terminal, and the
spec is explicit: "the only bytes a terminal writes back are the feature
detection reply, which contains nothing from any report. Ids, titles, and
messages are never sent back, and there is no way to read records." A terminal
that grows OSC 7501 support therefore does **not** feed Muster: Muster is a
bar, not a terminal, so it reads its own JSON records and reaches the pty
through `bin/muster-tap`.

## Vocabulary

| `state` | Meaning | Muster |
|---|---|---|
| `idle` | at rest, waiting for the next instruction | plain card |
| `working` | running, may carry `progress` | accent rim, breathing |
| `done` | finished, the user has not seen the result | accent rim, held; alert |
| `blocked` | cannot continue without the user; `kind` says what | urgent rim; no sound/notification (the urgent card is the signal) |
| `error` | failed and stopped | urgent rim; alert |
| `clear` | remove the record (a command, never stored) | record deleted |

`kind` (blocked only) is `permission`, `question`, or `auth`; the panel renders
it as "needs permission" / "has a question" / "needs sign-in". `progress` is an
integer 0–100. `id` is a hierarchical record id (`build/test`).

## Wire vs. record

The wire is the escape sequence; the JSON record is Muster's internal bus, and
it carries the protocol keys plus what the spec deliberately leaves to the
consumer (a window/pane to focus, the working directory, the identity of the
terminal that owns the record).

| OSC 7501 wire | JSON record | Notes |
|---|---|---|
| `state=…` | `state` | one of the five above; a report without a state is ignored, never read as `working` |
| `kind=…` | `kind` | blocked only; an unrecognised value is absent, not an error |
| `progress=…` | `progress` | 0–100, or `-1` for absent; a value outside that range is absent |
| `id=…` | `recordId` | display label; never a path, never a command-line argument |
| `app=…` | `agent` | stable program name; folds to omarchy's agent ids |
| `title=…` (base64) | `name` | short label |
| `msg=…` (base64) | `message` | one line; shown for blocked/done/error |
| — | `schemaVersion` | `2` |
| — | `sessionId` | the tap's own name for the session (`tap-<pid>-<token>…`) |
| — | `cwd`, `project` | where the session runs; `project` is the basename of `cwd` |
| — | `pid` | the agent's pid; a hint for display and focus, not the identity |
| — | `windowAddress` | the Hyprland window, looked up once at start |
| — | `herdrPane`, `tmuxPane`, `tmuxSocket` | the multiplexer pane the session runs in, if any |
| — | `terminalId` | a stable id for the tap that owns the record (`tap:<pid>:<token>`) |
| — | `updatedAt` | ms epoch; drives staleness |

That is the whole contract: **no `lastPrompt`, no `completedRuns`, no `seq`,
no `notifyContent`.** The protocol carries neither a prompt nor a run
counter, so the record has nowhere to put them. A finished run is recognised
by the **state edge** into `done`/`error`, not by a counter. A run that settled
after Muster started is announced once even if a scan missed the working edge;
a record already settled before Muster started stays silent.

The writer caps every field and the whole record at 64 KiB; the reader
(`Model.js`, `Record.qml`) treats the record as untrusted and strips control
characters and bidi overrides from every string.

## Feature detection

A program asks whether the terminal understands the protocol, and a supporting
terminal answers:

```
program  → OSC 7501 ; ? ST
terminal → OSC 7501 ; ? : states=idle,working,done,blocked,error : kinds=permission,question,auth ST
```

A reply without `states` means exactly those five states, and a reply without
`kinds` means exactly those three kinds; the lists are fixed and do not change
in later revisions, so a program can ask for a state it knows and fall back to
one that is present. A program that gets no reply — or that sees the reply to
the device-attributes query (`CSI c`) first — treats the protocol as
unsupported and sends nothing. That is why pi, Claude Code and the other
probe-gated emitters stay silent inside tmux or under Ghostty 1.3.1.

`bin/muster-tap` answers the query on the pane's behalf, which is what makes a
native emitter work under a terminal that does not. The query is still
forwarded, so a terminal that does answer is not silenced either, and the tap
answers a bounded number of them (32) so a program that asks in a loop cannot
make it write to the pty forever.

## Records, ids and clearing

A terminal holds one record per id, and **each report replaces its record
completely**: a key missing from the report is missing from the record
afterwards. A report with no `id` addresses the **root record**.

- `id` is hierarchical: at most 8 levels of at most 32 characters, so at most
  **263** characters in all (8 × 32 + 7 separators). An id that breaks the
  grammar breaks the whole report — it is not filed under the root, because
  that would overwrite an unrelated record.
- A record without an `app` takes it from its nearest ancestor that has one
  (its own remembered app first, then the parent, then the root).
- `state=clear` is a command, not a state: it removes the addressed record
  **and every record beneath it**. A clear with no id removes every record of
  that terminal.

`bin/muster-tap` keeps a **registry** per tap: one entry per protocol id, the
empty id being the root. The root record is filed under the session name
`tap-<pid>-<token>`, a child under `tap-<pid>-<token>-<safe id>-<digest>`, and
every record of the tap carries the `terminalId` `tap:<pid>:<token>`. The bar
keeps one card per record file, so one tap can own several records at once.
The digest in a child's name is always appended: a lossy token alone could be
spelled out by hand and would then name the file of another id, so one
program could delete the record of another.

The tap caps its own registry at 64 records (the spec's minimum; the spec's
256 is the maximum) and evicts the least recently updated one. A record is
written where the report is read — one small file and one rename, no `fsync`
— behind a rate cap, so a program that reports in a burst cannot turn the tap
into a file-system benchmark. The bytes going *out* to the terminal are queued and
drained by a bounded writer thread, so a terminal that stops reading cannot
freeze the tap in front of it. The tap pins the focused Hyprland window once
at start, so a record does not pay for a compositor walk on every write. It
sets `MUSTER_TAP=1` for the child, so anything else that watches the same
session directory can stand down.

## Lifetime

The spec ties records to events the terminal already sees:

- `working` and `blocked` are dropped on process exit and on a new shell prompt
  (OSC 133 `A`). `done` and `error` survive both. **No heartbeat is required
  by the spec** — a report is a snapshot, and a terminal must not require the
  program to re-send to keep a record alive.
- The tap drops the live records when its child exits and when a shell prompt
  appears, and leaves a settled `done`/`error` behind for the user.
- Muster adds its own clock on top: a record whose writer stopped goes stale
  after `staleAfterSec` (120 s); a settled record (`done`/`error`) ages on the
  much longer `settledAfterSec` clock (six hours), and the prune drops any
  record after seven days.
- Focusing a settled session is the acknowledgement the spec leaves to the
  consumer: the card stops reading as `done` and falls back to `idle`.

## Limits

The limits are the spec's, and the tap enforces every one of them:

| Limit | Value |
|---|---|
| whole sequence | 4096 bytes |
| key | 16 characters |
| `app` | 32 characters |
| `id` | 263 in all (32 per segment, 8 levels) |
| `title` | 256 encoded / 192 decoded |
| `msg` | 2732 encoded / 2048 decoded |
| records per tap | 64 (the spec's minimum) |

The record's own caps match the wire limits, so a conforming report is never
cut short: `name` 192, `message` 2048, `agent` 32, `sessionId` 64, `cwd`
1024, `project` 256. The whole record stays under the 64 KiB the reader
accepts.

## Security

Same-user processes are **inside** the trust boundary: the records are
`0600` in a `0700` directory, but any process running as you can still read,
write or delete them. The protocol and the tap protect against other local
users, malformed reports and a hostile child confusing the relay; they are not
an isolation boundary between two programs running as the same user.

The sequence is untrusted input from a program that already controls the
screen, so Muster applies the same rules the spec does:

- free text is base64 on the wire; **a report is discarded whole** if its
  base64 does not decode, if the decoded text contains a control character, or
  if it breaks a limit. Nothing from a discarded report is applied — a bad
  `title` does not cost you the `state` next to it;
- unknown keys are ignored, a repeated key keeps the last value, a malformed
  pair is skipped, and a pair whose value has a byte outside the wire charset
  is skipped;
- the limits are the spec's: see the table above.

And the writer itself is small enough to audit:

- **it is Python, in one file, with the standard library only** — no shell
  pipeline, no `jq`, no `flock`, no lock file, no writer process, and no
  subprocess in the write path (the only subprocess is a read-only `hyprctl`
  at start-up);
- the record is written to a staging file in the sessions directory and
  renamed onto its final name, so a reader never
  sees half a record;
- the staging file is created with `O_EXCL` on a random name, so a same-user
  writer that planted a hardlink cannot have a write redirected at another
  file;
- the sessions directory is opened **once**, with `O_NOFOLLOW`, and every
  write and every removal goes through that descriptor: a same-user process
  that renames the directory or plants a symlink at any component of the path
  cannot redirect a record;
- the directory chain is created with mode `0700` and every component is
  refused when it is a symlink, not a directory or not owned by this user; the
  mode is set through the descriptor and read back, so a filesystem that does
  not enforce POSIX modes is a refusal rather than a quiet leak;
- a record is published with mode `0600`, and the same read-back refuses to
  publish it on a filesystem that ignores the mode;
- a terminal never sends a record back: the only reply is the feature-detection
  answer, and it contains nothing from any report.

## What the tap implements now, and what is deferred

Implemented now:

- the feature-detection reply, with the `states` and `kinds` lists;
- a per-tap registry: one record per protocol id, the root plus its children;
- `app` inheritance from the nearest ancestor;
- root and child `clear`;
- dropping the live records on a new shell prompt (OSC 133 `A`) and on the exit
  of the child, with `done`/`error` surviving both;
- whole-report validation, the spec's limits and the field caps, all of it in
  `bin/muster-tap`.

Deferred (a full terminal model, and deliberately not part of this branch):

- the **256-record maximum** per terminal: the tap deliberately uses the
  spec's 64-record minimum, which is enough for one terminal and bounds the
  cleanup work;
- a **full reset** — RIS or DECSTR — reported as a clear of every record;
- the alternate screen, and any hierarchy beyond the ids a program actually
  reports;
- an **enrichment lane**: anything that would add a prompt, a session name or
  a run counter to the record. The protocol carries none of it, and this
  branch does not guess it.
